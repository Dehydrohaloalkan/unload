# Unload.ProjectSync

Консольный инструмент для безопасного переноса изменений из проекта разработки в
переименованную production-копию. Например, путь
`backend/Unload.Api/Program.cs` может сопоставляться с
`backend/IIU.Api/Program.cs`, а `namespace Unload.Api` — с
`namespace IIU.Api`.

Инструмент:

- сначала строит план и ничего не изменяет;
- показывает новые, изменённые, защищённые и production-only файлы;
- позволяет выбрать отдельные файлы по номерам или диапазонам;
- переименовывает пути и содержимое текстовых файлов;
- умеет показывать и применять файлы из одного выбранного Git-коммита;
- не удаляет production-only файлы при сравнении папок; удаление возможно только
  для явно выбранного `DELETE` из Git-коммита;
- перед обновлением существующего файла сохраняет его резервную копию.

## 1. Подготовить конфигурацию

Скопируйте `project-sync.example.json` в отдельный файл `project-sync.json`:

```powershell
Copy-Item .\tools\Unload.ProjectSync\project-sync.example.json .\project-sync.json
```

Откройте полученный файл и замените `IIU`/`iiu` на настоящее рабочее название.
В примере используется точная замена `Unload.` → `IIU.`. Точка важна: она
переименует `Unload.Api` и namespace `Unload.Api`, но не изменит внутренние имена
классов `MainUnloadTask` и методов `AddUnloadRuntime`.

Главные секции:

| Секция | Назначение |
|---|---|
| `renames` | Последовательные замены в относительных путях и выбранных текстовых файлах |
| `pathMappings` | Отличия структуры каталогов между development и production |
| `namespaceMappings` | Перенос отдельных C#-типов в другой namespace и добавление нужного `using` |
| `ignore` | Файлы не сравниваются и не показываются |
| `protected` | Отличия показываются, но файл нельзя выбрать для автоматической замены |
| `transformTextIn` | Файлы, внутри которых применяются `renames` |
| `backupDirectoryName` | Каталог резервных копий внутри production-проекта |

Например, если Angular лежит в development по пути `web/webApp`, а в production —
прямо в `web`, добавьте правило префикса:

```json
"pathMappings": [
  { "from": "web/webApp", "to": "web" }
]
```

Правило применяется к самому каталогу и ко всем файлам внутри него. Если правил
несколько, выбирается самое конкретное (с самым длинным `from`).

Если отдельный C#-тип находится в production в другом namespace, это также
фиксируется один раз в конфигурации:

```json
"namespaceMappings": [
  {
    "symbol": "RunnerEvent",
    "from": "Unload.Core",
    "to": "IIU.Core.Domain"
  }
]
```

Для файла, объявляющего `RunnerEvent`, инструмент изменит namespace. В остальных
C#-файлах, где используется этот тип, он добавит `using IIU.Core.Domain;` и
сохранит обычный `using IIU.Core;`, который может быть нужен другим типам.

Шаблоны записываются через `/` и поддерживают:

- `*` — любые символы внутри одного сегмента пути;
- `**` — любое количество вложенных каталогов;
- `?` — один символ.

Примеры:

```json
{
  "ignore": [
    "docs/drafts/**",
    "**/*.log"
  ],
  "protected": [
    "**/appsettings.Production.json",
    "backend/IIU.DataBase/Services/**"
  ]
}
```

`protected` проверяется и по исходному пути, и по уже переименованному целевому
пути. Поэтому в нём можно указывать имена production-проекта.

Замены выполняются буквально, с учётом регистра и в указанном порядке. Не
добавляйте широкую замену `Unload` → `IIU`, пока preview не подтвердит, что нужно
переименовать также классы `MainUnloadTask`, `ExtraUnloadTask` и похожие символы.

Независимо от конфигурации инструмент всегда игнорирует опасные или генерируемые
каталоги: `.git`, `bin`, `obj`, `node_modules`, `.angular`, `dist`, `.tools`,
`graphify-out`, `output`, `observability`, `ftp-root` и `_sync-backups`.

## 2. Предварительно посмотреть различия

Из корня репозитория:

```powershell
dotnet run --project .\tools\Unload.ProjectSync -- `
  --source "D:\Projects\Unload" `
  --target "D:\Production\IIU" `
  --config ".\project-sync.json" `
  --preview
```

`--preview` гарантирует, что файлы не будут изменены.

Обозначения отчёта:

| Статус | Значение |
|---|---|
| `ADD` | Файла ещё нет в production, его можно добавить |
| `UPDATE` | Файл отличается, его можно обновить |
| `DELETE` | Файл удалён выбранным Git-коммитом; перед удалением будет создан backup |
| `PROTECTED` | Файл отличается, но конфигурация запрещает его замену |
| `TARGET-ONLY` | Файл существует только в production и не будет удалён |

Совпадающие и игнорируемые файлы не печатаются по одному, чтобы отчёт оставался
читаемым.

## 3. Интерактивно выбрать файлы

Запустите без `--preview`:

```powershell
dotnet run --project .\tools\Unload.ProjectSync -- `
  --source "D:\Projects\Unload" `
  --target "D:\Production\IIU" `
  --config ".\project-sync.json"
```

После отчёта появится нумерованный список безопасных `ADD` и `UPDATE`. Можно
ввести:

```text
1,4,7-12
```

или выбрать всё:

```text
all
```

После выбора программа сразу переносит отмеченные файлы. Пустой выбор ничего не
меняет, поэтому сам выбор номеров или `all` служит подтверждением операции.

## 4. Применить все безопасные изменения

Для повторяемого запуска:

```powershell
dotnet run --project .\tools\Unload.ProjectSync -- `
  --source "D:\Projects\Unload" `
  --target "D:\Production\IIU" `
  --config ".\project-sync.json" `
  --apply-all
```

Дополнительное подтверждение словом `APPLY` не запрашивается. Старый параметр
`--yes` пока принимается для совместимости с готовыми скриптами, но больше ни на
что не влияет:

```powershell
... --apply-all --yes
```

## 5. Применение изменений по Git-коммитам

Git-режим не сравнивает весь проект. Вы выбираете один commit из репозитория
разработки, после чего инструмент показывает только файлы, изменённые этим
commit.

Незакоммиченные изменения исходного проекта в этом режиме не учитываются.
Production-папка не обязана быть Git-репозиторием. Инструмент не создаёт commit и
не выполняет Git-команды внутри production — после проверки это делает оператор.

### 5.1. Интерактивно выбрать commit

Запустите:

```powershell
.\Unload.ProjectSync.exe `
  --git `
  --source "D:\Projects\Unload" `
  --target "D:\Production\IIU" `
  --config ".\project-sync.json" `
  --preview
```

Появится список последних коммитов:

```text
   1. a1b2c3d  2026-08-07  Исправлена обработка выгрузки
   2. e4f5a6b  2026-08-06  Добавлена проверка конфигурации
```

Введите номер. Инструмент сравнит выбранный commit с его первым родителем и
покажет только изменения, внесённые этим commit. Для merge commit используется
сравнение с первым parent.

### 5.2. Выбрать файлы и применить

Уберите `--preview`, снова выберите commit, затем отметьте необходимые файлы:

```text
1,3-7
```

Git-режим понимает:

- добавление файла;
- изменение файла;
- Git rename;
- удаление файла.

При rename старый production-путь удаляется, а новый создаётся. Перед изменением
или удалением существующий файл попадает в `_sync-backups`.

`PROTECTED` показываются в отчёте, но выбрать их нельзя. Их изменения нужно
перенести вручную.

После переноса инструмент не изменяет Git production-проекта. Проверьте сборку,
просмотрите `git diff` в production и создайте commit самостоятельно.

### 5.3. Указать commit сразу

Можно передать hash, tag, branch или `HEAD`, не выбирая commit из списка:

```powershell
.\Unload.ProjectSync.exe `
  --git `
  --source "D:\Projects\Unload" `
  --target "D:\Production\IIU" `
  --config ".\project-sync.json" `
  --commit "a1b2c3d" `
  --apply-all
```

`--apply-all` применяет все доступные `ADD`, `UPDATE` и `DELETE`. Старый `--yes`
можно оставить в существующем скрипте, но он больше не нужен.

## 6. Резервные копии

При каждом запуске, который обновляет существующие файлы, создаётся папка:

```text
D:\Production\IIU\_sync-backups\2026-08-07_14-30-00\
```

Внутри сохраняются исходные production-файлы с прежней структурой каталогов.
Новые файлы не копируются в backup, потому что до синхронизации их не было.
Файлы, удаляемые Git-коммитом, сохраняются в backup перед удалением.

Инструмент не удаляет старые backup-папки автоматически.

## 7. Собрать отдельный Windows exe

Если на машине запуска не хочется выполнять `dotnet run`, можно собрать один
самодостаточный файл:

```powershell
dotnet publish .\tools\Unload.ProjectSync `
  -c Release `
  -r win-x64 `
  --self-contained true `
  -p:PublishSingleFile=true
```

Результат находится в:

```text
tools\Unload.ProjectSync\bin\Release\net10.0\win-x64\publish\
```

Положите рядом с exe свой `project-sync.json` либо каждый раз передавайте путь
через `--config`.

## Ограничения и безопасный порядок работы

Инструмент сравнивает итоговые файлы, но не умеет объединять две разные правки
внутри одного файла. Если production-файл содержит дополнительную логику, внесите
его в `protected` и объединяйте вручную.

Рекомендуемый порядок:

1. Закоммитить или сохранить изменения обоих проектов.
2. Запустить `--preview`.
3. Проверить `PROTECTED` и `TARGET-ONLY`.
4. Интерактивно выбрать файлы.
5. Собрать и протестировать production-проект.
6. Только после успешной проверки удалить ненужные backup-папки вручную.

Нельзя указывать одну и ту же папку как `source` и `target`. Также одна из этих
папок не может находиться внутри другой — программа остановится до сравнения.
